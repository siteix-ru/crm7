# Развёртывание CRM7

Один хостинг может обслуживать несколько проектов CRM7 в разных категориях:
лендинг в корне, прод и демо — в подкаталогах. Каждый проект — самостоятельная
копия (сборка фронтенда + каталог `api/` + `storage/`) со своим конфигом и своей
базой данных. Сборка фронтенда не привязана к корню: пути относительные, адрес
API по умолчанию — `./api/v2` (внутри своей категории).

## Структура каталогов

```
/public_html/                 ← корень сайта (лендинг и т.п.)
  demo/                       ← категория «демо»
    index.html, assets/…      ← сборка фронтенда (frontend/dist)
    config.js                 ← window.CRM_CONFIG (адрес API, название приложения)
    api/                      ← копия каталога api/
      public/                 ← точка входа (index.php, router.php, .htaccess)
      src/, db/, bin/         ← код, миграции, cron
      config/.env             ← настройки проекта (база, базовый путь, почта)
      storage/, var/          ← файлы и логи (вне webroot)
  prod/
    … то же для прод-проекта
```

## Подготовка нового проекта

1. Скопировать `frontend/dist` в каталог категории (например `demo/`).
2. Скопировать каталог `api/` в `demo/api/`.
3. В `demo/api/config/.env` задать:
   - `API_BASE_PATH=/demo/api/v2` — префикс пути API (локально — `/api/v2`);
   - `DB_HOST`, `DB_PORT`, `DB_NAME=<своя база>`, `DB_USER`, `DB_PASS`;
   - `APP_URL=https://сайт/demo`, `CORS_ORIGIN` — если фронтенд на другом домене;
   - `APP_KEY` и `DB_CONFIG_KEY` — случайные ключи (`openssl rand -hex 32` для каждого); `DB_CONFIG_KEY` шифрует пароль в `config/database.json`, хранится только в `.env` и не должен попадать в Git или публичные ответы API.
4. Создать базу и применить миграции:
   ```sql
   CREATE DATABASE crm_demo CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   GRANT ALL PRIVILEGES ON crm_demo.* TO 'crm_app'@'localhost';
   ```
   ```
   php demo/api/bin/migrate.php
   php demo/api/bin/seed-dev.php --password=…     # только для демо/тестового проекта
   ```
5. Cron: `php demo/api/bin/cron.php` (рассылки отчётов, SLA, передачи клиентов).

### Права конфигурации (обычный Linux)

Каталог `demo/api/config` должен принадлежать пользователю PHP-FPM (например
`www-data`) и иметь режим `0750`, а файлы `.env`, `database.json`, `database.json.bak`,
`database.json.lock` и временные файлы — `0600`. Пример для Debian/Ubuntu:

```bash
chown -R www-data:www-data demo/api/config
chmod 750 demo/api/config
chmod 600 demo/api/config/.env demo/api/config/database.json* 2>/dev/null || true
```

Права записи на каталог необходимы: `SafeConfigFileWriter` создаёт уникальный
temp-файл, пишет backup и выполняет atomарный `rename`. Достаточно прав файла
не хватит. В Docker используется тот же принцип с UID/GID 82 (`www-data` в
Alpine): setup-site задаёт `chown -R 82:82 config`, `chmod 750 config`,
`chmod 600 config/.env`.

Не делайте конфигурационные файлы доступными всем (`0644` и выше): даже
зашифрованный пароль БД и ключ в `.env` остаются чувствительными. После ручного
копирования файлов или изменения владельца восстановите права перед запуском PHP.

### Политика смены сервера БД через UI

`DatabaseHostPolicy` разрешает через админку только текущую пару «хост:порт».
Переменные ниже задают исключения; источник истины — серверный `.env`, а не
frontend.

- `DB_ALLOW_HOST_CHANGE` — разрешает ли админка сменить хост БД. Значение по
  умолчанию `false` (безопасный режим): любая попытка указать другой хост
  отклоняется с ошибкой `host_change_disabled`. Включать только при реальной
  необходимости.
- `DB_HOST_ALLOWLIST` — список **точных** hostname или IP через запятую.
  Записи нормализуются (регистр, завершающая точка, канонический вид IP);
  сравнение строгое по нормализованному значению. CIDR, wildcard и альтернативные
  порты не поддерживаются. Пустой список **не** означает «разрешены все адреса»:
  при включённой смене хоста любой адрес вне списка отклоняется с
  `host_not_allowed`.
- Текущая конфигурационная пара `DB_HOST` + `DB_PORT` разрешена полностью и в
  allowlist не нуждается. Изменение `DB_PORT` через UI запрещено **всегда** —
  в том числе при сохранении текущего `DB_HOST` (`port_change_disabled`): порт
  считается частью разрешённой пары. Включение `DB_ALLOW_HOST_CHANGE` разрешает
  только смену `DB_HOST` и **не даёт права менять `DB_PORT`** — новый хост
  проверяется с тем же портом, что и текущий.
- Для hostname дополнительно выполняется DNS A/AAAA-резолвинг; отказ резолвинга
  (`host_resolution_failed`) или отсутствие адресов блокирует смену. Все
  полученные адреса проверяются на metadata-endpoint'ы.
- Metadata-адреса (включая `169.254.169.254`, `100.100.100.200`, `fd00:ec2::254`,
  `metadata`, `metadata.google.internal`, `instance-data` и их IPv6-эквиваленты)
  запрещены всегда — даже если явно указаны в allowlist.

Пример для Docker (сервис БД с host `db`, хост через UI не меняется):

```ini
DB_HOST=db
DB_PORT=3306
DB_ALLOW_HOST_CHANGE=false
DB_HOST_ALLOWLIST=
```

Пример для обычного Linux (локальная БД):

```ini
DB_HOST=127.0.0.1
DB_PORT=3306
DB_ALLOW_HOST_CHANGE=false
DB_HOST_ALLOWLIST=
```

Если смена хоста действительно нужна, включите флаг и явно перечислите
разрешённые адреса (например, `DB_HOST_ALLOWLIST=new-db-host`); `DB_PORT` при этом
остаётся прежним — разрешение смены `DB_HOST` не распространяется на порт, —
а пароль для нового адреса должен быть указан в админке.

## Доверенные proxy и клиентский IP

`App\Http\Request::clientIp()` определяет IP клиента для rate limiting и аудита.
`TRUSTED_PROXIES` — список IP или CIDR через запятую в `.env`. **По умолчанию
список пуст**: `X-Forwarded-For` и `X-Real-IP` от произвольного клиента
игнорируются, используется `REMOTE_ADDR`. Приватные адреса не считаются
доверенными автоматически.

Если непосредственный источник запроса (`REMOTE_ADDR`) входит в список,
`X-Forwarded-For` разбирается справа налево: доверенные адреса цепочки
пропускаются, первый недоверенный адрес считается клиентом. `X-Real-IP`
принимается только от доверенного источника и только если в XFF нет подходящего
адреса. Некорректные и пустые значения отбрасываются; при отсутствии
`REMOTE_ADDR` возвращается `0.0.0.0`.

Примеры:

```ini
# Прямой доступ к PHP (без reverse proxy) — доверенных proxy нет
TRUSTED_PROXIES=

# Docker Compose: nginx/web в internal-сети с фиксированным IP
TRUSTED_PROXIES=172.30.0.2

# Обычный Linux: Caddy на том же хосте проксирует на 127.0.0.1:8080
TRUSTED_PROXIES=127.0.0.1
```

Для Docker-варианта зафиксируйте IP `web` в `compose`, чтобы он не менялся при
пересоздании контейнера:

```yaml
networks:
  internal:
    ipam:
      config:
        - subnet: 172.30.0.0/16
services:
  web:
    networks:
      internal:
        ipv4_address: 172.30.0.2
```

Назначение — сделать `REMOTE_ADDR` в PHP стабильным и совпадающим со значением
`TRUSTED_PROXIES`. Прокси (Caddy/nginx) должен дописывать клиентский адрес в
`X-Forwarded-For`; закрытый напрямую порт 8080 дополнительно исключает обход
прокси. При прямом доступе к PHP forwarded-заголовки просто игнорируются.

Переписывание URL для фронтенда не нужно — используется hash-роутинг.
Для API на Apache положить в `demo/api/.htaccess`:

```apache
RewriteEngine On
RewriteRule ^ public/index.php [L]
```

На nginx:

```nginx
location /demo/api/ {
    try_files $uri /demo/api/public/index.php?$query_string;
}
```

## Адрес API без пересборки

`demo/config.js` (рядом с `index.html`) задаёт адрес API на этапе запуска:

```js
window.CRM_CONFIG = { apiV2Base: './api/v2' };
```

Если API размещён в другом месте (например, общий для нескольких фронтендов) —
достаточно поправить `config.js`, пересборка не требуется. Переменные
`VITE_API_V2_BASE` / `VITE_API_BASE` при сборке и `window.CRM_CONFIG` работают
как переопределения; по умолчанию — относительный `./api/v2`.

## База данных из интерфейса администратора

Настройки → «База данных» (уровень 50+): сервер, порт, база, пользователь,
пароль (пустое поле — «не менять»). Кнопка «Проверить подключение» проверяет
соединение, «Сохранить» — проверяет и записывает `demo/api/config/database.json`
(предыдущий файл — `database.json.bak`). Приоритет: `database.json` → `.env` и
переменные окружения. После смены базы войдите заново — сессии хранятся в базе.

## Несколько проектов в одной СУБД

Каждый проект использует отдельную базу на общем сервере MySQL/MariaDB —
штатный способ изоляции: свои таблицы, пользователь и бэкапы, никаких правок
SQL. База выбирается в `config/.env` или в интерфейсе администратора.
Общая база с префиксом таблиц потребовала бы переписать все запросы и не даёт
выигрыша на обычном хостинге.

## Проверка после развёртывания

- `https://сайт/demo/` открывается, статика и `config.js` отдаются (200);
- вход в систему и список заявок работают — значит, путь API и база верны;
- в Настройках → «База данных» источник и параметры соответствуют ожидаемым;
- `https://сайт/demo/api/v2/health` (или любой публичный маршрут) отвечает;
- cron выполняется по расписанию.

## Восстановление доступа

- **Забыт/сменён пароль администратора.** Пересоздать стандартные учётные записи
  (если их нет): `php demo/api/bin/seed-dev.php --password=<новый пароль>`.
  Существующие логины не трогаются, отсутствующие создаются заново.
- **Смена базы данных «в никуда».** Переключение в админке разрешено только для
  базы с таблицами CRM и активным администратором; если доступ всё же потерян —
  удалить `demo/api/config/database.json` (или вернуть `database.json.bak`),
  настройки снова возьмутся из `.env`.
- **Потерян последний администратор.** API не даёт заблокировать или понизить
  последнего активного администратора (50+), нельзя заблокировать себя и сменить
  свою роль; администратор (50) не может управлять сисадмином (90). Если учётные
  записи повреждены вручную в базе — восстановить через `seed-dev.php`.
