# CRM7 Navigation 2.0 — архитектурная спецификация

Статус: проект внедрения, ожидает утверждения владельцем.
Дата: 2026-11-26.
Обновлено: 2026-11-26 — принята целевая модель бокового меню ChatGPT-типа (два состояния Rail, независимые accordion, навигационная поисковая модалка).
Основа: независимая экспертиза пяти агентов (Senior UX Architect, Senior UI Designer, UX Researcher/Product Designer, Accessibility & Responsive UX Expert, Product Critic/Contrarian), результаты зафиксированы в отчёте OpenCode.

Местоположение: `docs/navigation-2.0.md`. В репозитории принята плоская структура `docs/*.md` (`architecture.md`, `ui.md`, `plan.md`), поэтому каталог `docs/architecture/` не создаётся.

## 1. Executive Summary

Текущая навигация CRM7 рабочая, но упёрлась в потолок: горизонтальный Header содержит 8 основных разделов и 5–6 утилит; при ширине ≤1180 px подписи исчезают, и Header превращается в панель иконок. При этом мобильная модель (нижние табы + «Ещё») и тёмная тема — сильные стороны, которые нельзя потерять.

Эксперты пришли к общему ядру: нужна иерархическая, role-aware навигация с **одним источником истины** о доступности, чётким разделением global / contextual / entity navigation и сохранением контекста. Разногласия касались формы: широкий постоянный Sidebar vs компактный Rail.

**Окончательное решение:** CRM7 Navigation 2.0 — **Adaptive Application Rail + Contextual Workspace**.

- Постоянный **Rail** заменяет основную навигацию в Header, но не статусные каналы.
- **Compact** — режим по умолчанию на всех desktop/tablet ширинах: логотип CRM7, иконки основных блоков, tooltip по наведению и фокусу, раскрытие логотипа по наведению и Flyout по клику на блок.
- **Expanded** — раскрытое дерево навигации с названиями блоков, независимыми accordion, вложенными разделами и страницами; доступно по ручному переключению при viewport ≥768 px.
- **Topbar** сохраняет Chat, Notifications, Cart и Profile с бейджами; поиск вынесен в Expanded Rail и отдельную навигационную поисковую модалку, а не в Topbar.
- **Bottom Navigation** на телефоне сохраняется как единственная мобильная система меню и получает состав из того же `visibleNav`.
- Всё строится на **едином Navigation Registry**, который генерируется backend и отражает реальные права/модули.
- Phase 0 и Phase 1 реализованы локально. Далее: Phase 2 — Tree Navigation, независимые accordion, Context Preservation и навигационная поисковая модалка; Phase 3 — Command Palette `⌘/Ctrl+K` и Recently visited; Phase 4 — polish и персонализация.
- Навигационная поисковая модалка и Command Palette — разные слои: первая ищет только доступные разделы и страницы, вторая — сущности и безопасные команды. Не допускаются два конкурирующих поисковых входа.
- Wide Sidebar-first, Workspace switcher, Favorites «по умолчанию», полный redesign карточек и таблиц — отвергнуты или отложены.

Итоговая оценка рекомендуемой модели: **8.6/10**.

## 2. Почему текущая модель должна эволюционировать

1. `.desktop-nav` имеет потолок ~8 пунктов; при `navCount > 6` включается класс `.many`, при ≤1520 px уменьшаются отступы, при ≤1180 px подписи скрываются (`display:none`), остаются иконки с `title`.
2. Административные экраны разбросаны: `#/settings/*`, `/admin/audit`, `/stocks/groups|types|price-types`, `/staff`. Нет единого узла «Система».
3. Chat/Cart — реальные модули (`Modules.php`), но поданные как «колокольчики»; на мобильном — 2 клика через «Ещё».
4. Доступность определяется в пяти местах: `Modules::guards()`, `/settings/app`, `AppShell` (`showClients/showStaff/...`), `App.svelte` (`NotFound`) и `$effect`-редиректы. Это уже приводило к дефекту M3 (клиенту показывались недоступные разделы).
5. Табы карточек не кодируются в URL; фильтры и поиск списков сохраняются, но скролл, активный чат-thread и `returnTo` — нет.
6. В дизайн-ревью зафиксировано 5 разных реализаций табов и доступность 4/10.

Эволюция требуется не ради «современного вида», а ради масштабируемости IA и устранения рассогласований прав.

### 4. Согласие экспертов
- Нужен единый декларативный реестр навигации и доступности.
- Нужно сохранить мобильную нижнюю навигацию и бейджи статусных каналов.
- Нужны role-aware фильтрация, стабильные URL и обратная совместимость deep links.
- Нужно разделить global / contextual / entity / action.
- Command Palette и Context Preservation дают реальный выигрыш.

### 5. Разногласия
| Вопрос | Позиции |
|---|---|
| Wide Sidebar | UI Designer — да как рама; Architect/Critic — нет; Accessibility — только ≥1280/1760 |
| Удалить Header-навигацию | UI/Architect — да с заменой; Critic — нет без метрик |
| Command Palette | Researcher/UI/Architect — must-have; Critic — cargo-cult до телеметрии |
| Recently/Favorites | Researcher — recently must-have; Critic — риск мертвых ссылок |
| Оценка текущей модели | от 5.7 до 7.5 |

### 6. Разрешение
- Принята модель **Rail + Contextual Workspace** вместо широкого Sidebar-first.
- Частично удовлетворён Critic: до любой визуальной замены выполняется **Phase 0** (реестр, URL, a11y-контракт, метрики). Итоговая актуализация: автоматического Expanded нет; ручной Expanded доступен от 768 px (см. §9–11).
- Частично удовлетворён Accessibility: compact обязательно имеет `aria-label`, tooltip по фокусу и видимое имя текущего раздела; drawer получает `inert` и полный focus-контракт.
- Частично удовлетворён Researcher: Recently visited входит в MVP, но только как безопасные ссылки с повторной проверкой прав.
- Critic не «опровергнут искусственно»: его аргументы перенесены в раздел 32 как риски с criteria пересмотра.

## 7. Финальный архитектурный вердикт

**Adaptive Application Rail + Contextual Workspace** — единственная рекомендуемая архитектура.

Принципы:
1. Один реестр навигации, backend-driven.
2. Backend authorization остаётся единственным источником права на действие.
3. Хром приложения укладывается в бюджет ширины: Rail 56 px по умолчанию; 232–260 px по явному выбору пользователя от 768 px.
4. Иерархия: рабочее пространство → основные блоки → подразделы → страницы. Не более трёх одновременно видимых навигационных уровней: global → contextual → entity.
5. Состояния accordion независимы и хранятся как пользовательские настройки отображения, отдельно от прав и от структуры `visibleNav`.
6. Состояние навигации отражается в URL; временное UI-состояние — в history state.
7. Мобильная навигация — отдельная зрелая система на том же реестре.
8. Поиск разделов — в навигационной модалке; глобальный поиск сущностей и команды — в Command Palette Phase 3. Два разных назначения, один стек фокуса и Escape.

## 8. Целевой Application Shell

```
┌───────────────────────────────────────────────────────────┐
│ Rail │ Topbar: [breadcrumb] [chat][bell][cart] [avatar]    │
│ 64/  ├─────────────────────────────────────────────────────┤
│ 232– │ Workspace: H1 + primary action                      │
│ 260  │ Contextual nav (chips / second-level rail)          │
│      │ Data surface (table / cards / form)                 │
└───────────────────────────────────────────────────────────┘

Expanded Rail: [CRM7] [search icon] [collapse]
               block 1 ▾ → subsections → pages
               block 2 ▸
               ... independent scroll ...
```

Rail слева, фиксированный, `height:100dvh`, фон `var(--surface)`, граница справа `1px var(--border)`. Topbar — 56 px, не вторая навигация. Workspace сохраняет текущие `max-width` 1280/1440/1600 с поправкой на ширину Rail.

## 9–11. Adaptive Rail, Expanded/Compact, Flyout

### Режимы (предварительные, требуют прототипа)

| Ширина | Режим по умолчанию | Rail | Примечание |
|---|---|---|---|
| ≥1280 | Compact | 56 px | ручной Expanded разрешён и сохраняется |
| 1024–1279 | Compact | 56 px | ручной Expanded разрешён и сохраняется |
| 768–1023 | Compact | 56 px | ручной Expanded разрешён; таблицы → карточки, чтобы не было horizontal overflow |
| <768 | Bottom Navigation | — | 4 таба + «Ещё» drawer |

**Единое правило breakpoint (актуализировано вручную):**
- Desktop Compact — viewport **от 768 px**;
- ручной Expanded — при viewport **от 768 px**;
- мобильная навигация — viewport **меньше 768 px**;
- автоматического Expanded нет.

Диапазон 720–767 px более не является неопределённым: он целиком относится к мобильной модели. Автоматического Expanded нет. Контрольные viewport для тестирования: **1920, 1600, 1440, 1280, 1279, 1024, 768, 767, 390, 360**.

### Compact (модель ChatGPT-подобного бокового меню)
- Верх: логотип CRM7. При наведении на логотип появляется иконка раскрытия меню; клик по ней доступен от 768 px.
- Ниже — только **основные блоки навигации** в виде иконок; не пытаться вместить все страницы и вложенные уровни.
- Названия блоков доступны через tooltip по наведению и по `:focus-visible`, с Escape и `aria-describedby`; `title` недостаточен.
- Клик по основному блоку открывает Flyout с его доступными подразделами и страницами.
- `aria-label` на каждом пункте; активный блок отмечен полосой и иконкой primary; на всех страницах `h1` содержит название текущего раздела.
- Footer: аватар/профиль, версия.

### Expanded
- Ширина 232–260 px (целевое значение 240 px).
- Верх: название системы **CRM7**, иконка поиска и иконка сворачивания меню.
- Ниже — полное дерево доступной пользователю навигации: основные блоки с названиями, внутри раскрытого блока — подразделы и страницы.
- Каждый блок имеет **собственное состояние accordion**; состояния блоков независимы.
- Дерево прокручивается независимо от Workspace; Workspace не меняет ширину при раскрытии/сворачивании блоков.
- Пункты: иконка 20 px + подпись 13 px; строка 40 px (44 на тач). Footer: Профиль, версия.

### Независимые состояния accordion
- Глобальное состояние Rail (Compact/Expanded) и состояния отдельных блоков не смешиваются.
- Пользователь может независимо раскрывать и сворачивать основные блоки; состояния разных блоков сохраняются независимо как пользовательские настройки отображения.
- Правило «раскрыта только одна группа» отменено: нет обоснованной причины ограничивать пользователя.
- При переходе на страницу автоматически раскрываются родительские группы активного маршрута; уже сохранённые состояния других блоков не сбрасываются.
- При изменении роли, доступных модулей или состава `visibleNav`: скрытые узлы удаляются из дерева, состояния удалённых блоков удаляются, состояния сохранившихся блоков остаются; недоступные разделы не восстанавливаются из старого состояния.
- Пользовательские состояния отображения не являются правами доступа и не влияют на backend-проверки.

### Иерархия
- Рабочее пространство → основные блоки → подразделы → страницы.
- Иерархия строится только из реальных модулей CRM7 и `visibleNav`; новые бизнес-разделы и маршруты не создаются.
- Не смешивать структурную иерархию, права доступа и пользовательские настройки отображения.

### Flyout
- В Compact основной блок — кнопка с визуальным индикатором вложенности; она открывает Flyout и имеет корректные `aria-expanded`/`aria-controls`.
- Flyout показывает доступные подразделы и страницы выбранного блока; конечные пункты — ссылки с прямой навигацией.
- Не пытаться дублировать полное дерево Expanded в Flyout.
- Flyout имеет `role="dialog"`; фокус внутри, Escape закрывает, фокус возвращается; не является третьим постоянным меню.

### Активное состояние
- Expanded: левая полоса 3 px `var(--primary)` + фон `color-mix(primary 8%, surface)` + текст primary/600.
- Compact: та же полоса + иконка primary.
- Не только цвет (WCAG 1.4.1).

## 12. Topbar

Окончательно:

| Элемент | Решение |
|---|---|
| Поиск | В Topbar не размещается; иконка поиска — в Expanded Rail, открывает навигационную поисковую модалку (§12.1). Command Palette `⌘K` — отдельный слой Phase 3 |
| Breadcrumbs | Только для глубоких страниц desktop; в Compact-режиме текущий раздел всегда виден в `h1`; на mobile — стрелка «назад» + заголовок |
| Chat | Обязательно, с бейджем, всегда виден |
| Notifications | Обязательно, с бейджем |
| Cart | Обязательно, с бейджем (если модуль включён) |
| Profile | только иконка профиля 18 px (аватар уменьшен до её размера), как чат/корзина/уведомления |
| Audit / About | Перенесены в Rail group «Система»; не в Topbar |
| Статус сети/демо-режима | Сохранить существующие полосы под Topbar |

Topbar не повторяет Rail. В нём остаются только статусные каналы и профиль.

### 12.1. Навигационная поисковая модалка

**Назначение:** быстрый переход к разделу или странице, которые уже есть в `visibleNav`. Это не глобальный поиск по сущностям и не Command Palette.

- Открытие: клик по иконке поиска в Expanded Rail. В Compact поиск доступен через раскрытие меню (от 768 px) или через Command Palette Phase 3.
- Модалка поверх Workspace: `role="dialog"`, `aria-modal="true"`, фокус сразу в поле, видимый focus, возврат фокуса к иконке поиска при закрытии.
- Закрытие: Escape, кнопка закрытия, выбор результата, клик по фону; приоритет Escape — search modal → palette → drawer → flyout → modal → tooltip.
- Клавиатура: ↑/↓/Home/End/Enter, `aria-activedescendant` для выделенного результата, `aria-live="polite"` для количества результатов.
- Визуальное выделение совпадений в названиях разделов/страниц; пустое состояние «Ничего не найдено».
- Источник результатов — только узлы `visibleNav`, доступные текущему пользователю. Недоступные разделы, модули и страницы в результаты не попадают.
- Выбор результата выполняет переход по маршруту узла и закрывает модалку; `returnTo` и состояние списка не изменяются в Phase 2.

**Архитектурная расширяемость:** поисковая модалка проектируется так, чтобы позже добавить поиск по сущностям CRM7 (клиенты, сотрудники, заявки, номенклатура) через отдельный провайдер результатов. Полноценная реализация глобального поиска сущностей в Phase 2 не входит.

**Граница с Command Palette:**
| | Навигационная поисковая модалка | Command Palette (Phase 3) |
|---|---|---|
| Вход | иконка в Expanded Rail | `Ctrl/Cmd+K` |
| Источник | `visibleNav` | сущности + доступные команды + recent |
| Назначение | найти раздел/страницу | выполнить действие или открыть сущность напрямую |
| Горячая клавиша | нет | да (`Ctrl/Cmd+K`) |
| Дублирование | не создаёт второй поисковый вход | не добавляет вторую иконку поиска |

Один стек модалок и один Escape priority; при появлении Command Palette навигационная модалка остаётся его частным режимом или скрывается, чтобы не было двух конкурирующих поисковых интерфейсов.

## 13. Workspace

- Один внятный холст; убрать card-in-card.
- Заголовок: H1 + одна primary-кнопка; метаданные 12 px muted.
- Второй ряд только для списков: поиск + фильтр/сортировка/вид ghost-иконки с бейджем активных фильтров.
- Область данных — одна surface со sticky-заголовком и sticky-пагинацией.
- Пустое состояние компактное: иконка 40 px, заголовок 14/600, одна CTA; не карточка на 500 px.
- Правило «одного синего»: на экране одна залитая primary-кнопка.

## 14. Contextual Navigation

Второй уровень живёт в URL и отображается чипами/компактным сайдбаром под заголовком:

- `#/requests?scope=mine|unassigned|overdue|drafts`
- `#/clients?state=pending|mine|pool`
- `#/stocks?tab=levels|lots|warehouses|groups|types|price-types`
- `#/staff?tab=staff|substitutions`
- `#/settings/:section/:sub` — существующая модель сохраняется и мигрирует в общий контракт.

Состояние кодируется в URL, а не только в localStorage. На мобильном — горизонтальная лента чипов под H1.

## 15. Entity Navigation

Единый контракт табов:
- `role="tablist"`, `role="tab"`, `aria-selected`, `tabpanel` с `aria-labelledby`.
- Активная вкладка `tabindex=0`, остальные `-1`; стрелки ←/→ (и ↑/↓ для вертикальных) + Home/End.
- Активный таб кодируется в URL: `?tab=history`, `?tab=files`, `?thread=ID`.
- Фокус при переключении остаётся на табе; `document.title` обновляется при hash-навигации.
- Иконки табов имеют видимые подписи на desktop; на mobile — подпись под иконкой не менее 11 px.

Entity-табы остаются внутри карточек и **не** попадают в Rail.

## 16. Mobile

Сохраняется текущая сильная модель:
- 4 основных таба + «Ещё»;
- приоритет табов по роли (не жёсткий order `Stocks → Requests → …`);
- «Ещё» — полноценный second-level доступ с группами «Разделы» и «Сервис», с агрегированным бейджем;
- Chat и Notifications доступны в Topbar (не хоронятся в drawer);
- touch-цели ≥44–48 px, подписи ≥11 px;
- drawer: `role="dialog"`, `aria-modal`, `aria-labelledby`, focus trap, Escape, restore focus, `inert`-фон, закрытие по фону и `matchMedia`;
- back navigation: видимая кнопка «Назад» + браузерная история; swipe-back остаётся дополнительным жестом;
- ≥4 слота на ≤360 px; пятый уходит в drawer.

## 18. Navigation Registry

### NavNode (структура)

```ts
interface NavNode {
  id: string;                 // 'requests', 'stock-lots', 'settings'
  label: string;              // локализованное название
  iconId: string;             // идентификатор из Icon.svelte
  group: 'work'|'stock'|'analytics'|'org'|'system';
  route: string;              // '#/requests'
  children?: NavNode[];       // не более 2 уровней
  capabilities: string[];     // ANY из списка
  settings?: string[];        // module.* флаги
  visibleWhen?: string;       // дополнительное условие
  badge?: { source: 'chat'|'notifications'|'cart'|'none' };
  presentation: {
    rail: boolean; topbar: boolean; bottom: boolean; drawer: boolean;
  };
  order: number;
  type: 'section'|'subsection'|'action';
  contextual?: string;        // какую contextual-навигацию открывает
}
```

### Server-driven видимость
- Backend (`/settings/app`) возвращает `visibleNav: NavNode[]`, уже отфильтрованный по `modules`, `capabilities`, `appSettings`.
- `Modules.php` остаётся источником описания модулей и API-guard.
- **`NavNode.capabilities` является производной от существующего `Modules::access`.** Ручное создание независимых capability или второго источника прав в Registry запрещено.
- Контрактные тесты проверяют соответствие Registry существующей политике доступа.
- Frontend рендерит зарегистрированный список в Rail / Topbar / bottom / drawer и **не вычисляет права заново**.
- `auth.can()` остаётся вторичной защитой UI, но не источником истины.
- Registry управляет только отображением навигации. Backend Authorization на каждый API-запрос сохраняется полностью; прямой URL и API остаются защищены существующими backend-проверками.

### Переход от текущего состояния
1. Phase 0: добавить `visibleNav` в `/settings/app`; оставить старые флаги для совместимости.
2. Phase 1: `AppShell` рендерит Rail из реестра; прежние проверки `showClients/showStaff/...` отключаются или заменяются отдельным PR.
3. Phase 2: `App.svelte` route-guard использует реестр вместо ручных проверок.
4. Phase 3: модули объявляют nav-contribution declarative; новый модуль не требует правки `AppShell`.

### MVP Phase 3 (фактически реализовано)
- `Ctrl/Cmd+K` — единый hotkey; отдельной иконки в Topbar нет. Повторное нажатие закрывает Palette; сочетание не перехватывается в `input`/`textarea`/`select`/`contenteditable`.

- Смена статуса, отправка сообщений, передача, удаление — только после отдельного контракта: права, подтверждение, ошибки, аудит, UX.

### Доступность
`role="dialog"`, `aria-modal="true"`, фокус в поле, `aria-activedescendant`, ↑/↓/Home/End/Enter, `aria-live` для count, Escape + restore focus, единый Escape priority: search modal → palette → drawer → flyout → modal → tooltip.

- Если Command Palette открыта, навигационная модалка не открывается повторно; используется один стек.
- При внедрении Phase 3 фиксируется один источник результатов и одна модель прав.

## 21. Recently visited

- Входит в MVP (решение по Researcher), но ограничено.
- **Фактически (Phase 3):** хранятся только базовые маршруты разделов (`/requests`, `/chat`, …) и их заголовки из `visibleNav`; сущностные ID и query-параметры не сохраняются. Это устраняет риск утечки чувствительных данных, но означает, что история сущностей (тип + ID) остаётся отложенной.
- Хранить **тип + ID + владельца** — требуется будущей истории сущностей; в текущей реализации достаточно `path + userId`.
- Не более 5 записей на пользователя. TTL записи — 30 дней с момента последнего обращения.
- При потере прав, удалении объекта или отключении модуля запись **удаляется**, а не только скрывается.
- Данные очищаются при смене пользователя; не допускается смешивание истории разных пользователей на общем устройстве (ключ storage включает ID пользователя).
- Пользователь может вручную очистить список через Command Palette («Очистить недавние»).
- Перед переходом повторно проверяются доступность маршрута, существование объекта и права; недоступные записи удаляются из списка.
- Показывать: в Command Palette (до ввода) и на стартовом экране до 3 последних сущностей.
- Исключать: временные черновики, чужие приватные чаты, документы без прав.

## 22–23. Context Preservation и URL contract

### Классы состояния

| Класс | Что хранится | Где |
|---|---|---|
| **URL state** | route, entity id, `tab`, `thread`, `scope/state`, `page`, `q`, `returnTo` | hash/query |
| **History state** | scroll position, transient modal stack | `history.state` |
| **User preferences** | filter sets, view mode, per-page, rail state, theme, recent | server preferences + localStorage |
| **UI state** | открытый flyout/drawer, временный фокус, hover | `$state`, не сохраняется |
| **Form drafts** | черновик заявки | существующий механизм `/requests/new?draft=…` |

Не помещать всё в URL: длинные фильтры и персональные настройки остаются в preferences.

### Сценарии
- Заявка → клиент → чат → заявка: `returnTo` и `?tab=` восстанавливаются.
- Уведомление → заявка → назад: возврат к `/notifications?filter=unread`, фильтр восстановлен.
- Склад → корзина → `/requests/new?from=cart` → заявка: поиск склада и страница сохраняются.
- Внутренний переход в чат: `?thread=ID` пишется в URL и восстанавливается браузерной кнопкой «Назад».

#### Валидация `returnTo`
- `returnTo` принимает только внутренние hash-маршруты формата `#/…`, максимальная длина — 128 символов.
- Маршрут проверяется по route allowlist и по актуальным правам пользователя.
- Запрещаются внешние URL, некорректные маршруты и циклические перенаправления.
- При недоступности целевого маршрута используется безопасный fallback: первый доступный пользователю маршрут по действующей серверной политике навигации (`visibleNav`) либо безопасная страница отказа в доступе.
- `#/requests` не закрепляется как универсальный fallback.

### Фактическое состояние (Phase 2C.1, реализовано локально)

- **URL:** `router` сохраняет query/hash; табы карточек заявки и клиента кодируются в `?tab=` и восстанавливаются при повторном открытии, смена таба не создаёт дублирующих записей истории (`replaceState`). `?thread=` чата и `?draft=` заявки используют уже существующий контракт и не изменены.
- **returnTo:** безопасный вход из списка заявок, уведомлений и карточек; валидация схемы/длины/allowlist на основе актуального `visibleNav`, запрет внешних URL, секретных query-ключей и циклов; недоступный маршрут не восстанавливается; в Topbar появляется кнопка «Назад» только для допустимого `returnTo`.
- **История и прокрутка:** `history.scrollRestoration = 'manual'`; позиция пишется в `history.state` через `replaceState` (новые записи не создаются), восстанавливается при Back/Forward, в том числе для переходов по обычным `<a href="#/…">`.
- **Фильтры/поиск/сортировка/страница:** переиспользуются существующие `filters.ts` + `/preferences/filters`; кэш localStorage теперь привязан к `userId`; restored-значения проверяются по типам. Уведомления получили такой же контракт (`filter`, `page`, `per_page`).
- **Черновики:** используется уже существующий серверный механизм `/requests/new?draft=…` с autosave и `pagehide`; дублирующий локальный черновик не создаётся.
- **Accordion:** состояния независимых групп уже привязаны к пользователю и очищаются при logout (Phase 2A).

**Изоляция и очистка:** ключи `crm.filters.<userId>.*` и `crm.nav2.*` персональны; при `clearSession()` отменяются отложенные записи фильтров и удаляются все локальные состояния навигации текущего пользователя. `localStorage` никогда не является источником прав: доступ к маршруту проверяется по серверному `visibleNav` и текущим capabilities.

**Осталось вне Phase 2C.1 (не реализовано):** единый компонент табов для всех карточек; `?tab=` для всех сущностей; `?q/page/sort/scope` в URL для всех списков; серверные пользовательские preferred view вместо localStorage; transient modal stack в `history.state`; Recently visited и Command Palette (Phase 3).

### Quick Actions (Phase 2C.2, реализовано локально)

**Принцип:** только безопасные навигационные команды из уже согласованного списка; никаких мутаций, отправки форм, поиска сущностей и новых прав.

| Действие | Маршрут | Условие доступности |
|---|---|---|
| Новая заявка | `/requests/new` | узел `requests` в `visibleNav`, модули `requests` и `sales`, capability `requests.create` |
| Открыть чат | `/chat` | узел `chat` в `visibleNav`, модуль `chat`, capability `chat.use` |
| Открыть настройки | `/settings` | узел `settings` в `visibleNav`, одно из `settings.manage`, `mail.manage`, `mail.send`, `messengers.manage` |

- Размещение: компактное меню в Topbar на desktop (≥768 px) и тот же список в drawer «Ещё» на мобильных; нижняя навигация не заменяется.
- Источник доступности — актуальный `visibleNav` + `auth.capabilities` + флаги модулей; отдельного реестра прав нет.
- Право проверяется дважды: при построении списка и непосредственно перед переходом. Серверные guard'ы маршрутов и бизнес-действий остаются обязательными; клиентское состояние не является авторизацией.
- ARIA/клавиатура: `role="menu"`/`menuitem`, `aria-expanded`/`aria-controls`, видимый focus, ↑/↓/Home/End, Enter, Escape с возвратом фокуса, закрытие по внешнему клику. Второй modal-стек не создаётся; мобильный drawer использует существующий focus trap.
- Матрица демо-ролей: root/admin — 3 действия; manager/client — «Новая заявка» и «Открыть чат» (без настроек).

**Отложено:** Quick Actions в Command Palette Phase 3 (переиспользуют тот же провайдер), любые мутирующие команды (смена статуса, отправка, удаление) — только после отдельного контракта; actions на сущностных страницах и пользовательская настройка набора.

## 24–26. Accessibility, Keyboard, UI Design System

### Обязательные требования
- Skip-link «К содержимому» первым в DOM + вторая skip-ссылка «К разделам» на мобильном.
- `aria-current="page"/"location"`, `aria-expanded`, `aria-controls`, `aria-haspopup`.
- Каждый accordion-блок Expanded — `<button aria-expanded aria-controls>`; состояние соответствует визуальному дереву. Flyout и поисковая модалка имеют те же атрибуты и явные имена.
- Явные `aria-label` на icon-only пунктах; видимый текст входит в имя (2.5.3).
- Tooltip по hover **и фокусу**, dismissible/hoverable/persistent (1.4.13); `title` недостаточен.
- Escape priority: search modal → palette → drawer → flyout → modal → tooltip. Не закрывать несколько слоёв сразу.
- `inert` на фоне drawer/modal; restore focus с fallback на `main`.
- Roving tabindex только в `tablist`; навигационные ссылки — естественный Tab.
- Visible focus 2 px + offset; в dark теме проверить контраст skip-link и badge.
- Touch targets ≥44 px (mobile), ≥48 px (rail items).
- `prefers-reduced-motion` сохранить.
- `aria-sort`, `scope="col"`, `<caption>` в таблицах.

### Design tokens
- Rail 64/72 px (Compact) и 232–260 px (Expanded); Topbar 56 px; строка Rail 40/44 px; иконка 20–24 px.
- Радиусы 8/12 px; тени мягкие; surface `var(--surface)`.
- Визуальная иерархия: основные блоки — 13/600, подразделы — 12.5/500, страницы — 12/400; отступ вложенности 16–20 px на уровень.
- Активный маршрут: левая полоса 3 px + оттенок primary + вес 600; активный блок в Compact — полоса и иконка primary; не только цвет (WCAG 1.4.1).
- Состояния: hover `var(--fill-tertiary)`, focus-visible 2 px с offset, active — оттенок и вес, disabled — пониженная контрастность без скрытия функции.
- Раскрытие/сворачивание accordion и Flyout — плавное 120–180 ms; `prefers-reduced-motion` отключает анимацию. Ширина Workspace не меняется при раскрытии блоков.
- Дерево Expanded имеет независимую вертикальную прокрутку; при большом количестве пунктов — виртуализация или «Показать ещё» внутри блока, не горизонтальный скролл страницы.
- Плотности: **Comfortable 44 px** (заявки, клиенты, уведомления), **Compact 36–40 px** (номенклатура, партии, аудит, отчёты), **Readable 64–72 px** (чат, превью).
- Desktop и mobile используют один реестр, но разные представления; поведение активного пункта и бейджей согласовано.
- Полный redesign карточек и форм — отдельный backlog.

## 29. Roadmap

### Phase 0 — Architecture Foundation
**Цель:** зафиксировать согласованный контракт навигации до визуальных изменений.
**Входит:** только согласованный контракт навигации (URL, a11y, responsive и compatibility как разделы контракта), серверный `visibleNav` в `/settings/app`, role-matrix и контрактные тесты; `NavNode.capabilities` выводится из `Modules::access`.
**Не входит:** реализация Rail, Topbar, Flyout и визуального Shell; отключение старых проверок навигации.
**Зависимости:** нет.
**Риски:** расхождение с существующими флагами.
**Acceptance:** `/settings/app` отдаёт корректный `visibleNav` для 5 ролей; контрактные тесты подтверждают совпадение Registry с `Modules::access`; все текущие URL работают.
**Тесты:** role matrix API + контрактные тесты Registry + frontend unit.
**Результат:** один согласованный контракт доступности навигации.
**Критерий завершения:** контракт принят, `visibleNav` доступен backend, role-matrix и контрактные тесты зелёные; существующие проверки в `AppShell`/`App.svelte` остаются активными.

### Phase 1 — Application Shell
**Цель:** Rail + Topbar + Workspace desktop/tablet.
**Входит (реализовано локально):** Rail 64/72 и базовый Expanded 240, Compact/Expanded, базовый Flyout, Topbar со статусными каналами (без поиска), Workspace, скрытие Header-nav, интеграция `visibleNav`, устранение дублирующих проверок видимости. Полное дерево, независимые accordion и поисковая модалка переносятся в Phase 2.
**Не входит:** palette, recently, entity tabs, изменения бизнес-логики.
**Зависимости:** Phase 0.
**Риски:** потеря ширины, регресс a11y.
**Acceptance:** 7 контрольных viewport без horizontal overflow; бейджи видны; skip-link/focus работают.
**Тесты:** e2e desktop/tablet, Lighthouse, role matrix.
**Результат:** новая оболочка.

### Phase 2 — Tree Navigation & Context Preservation
**Цель:** довести Rail до целевой модели ChatGPT-подобного меню и сохранить контекст работы.
**Входит:** иерархия «Workspace → основные блоки → подразделы → страницы»; Expanded с независимыми accordion; Compact с логотипом и Flyout по блоку; автоматическое раскрытие родителей активного маршрута; сохранение пользовательских состояний accordion; навигационная поисковая модалка; согласование мобильной навигации с общей иерархией; Quick Actions в согласованных местах; URL/history/preferences/drafts контракт; `returnTo`, scroll restoration, единый tab component.
**Не входит:** Command Palette `Ctrl/Cmd+K`, Recently visited, глобальный поиск по сущностям, мутации данных, полный redesign страниц.
**Зависимости:** Phase 0 + Phase 1 (реализованы локально).
**Риски:** рассинхронизация accordion и `visibleNav`, скачки ширины Workspace, дублирование поиска, сложные переходы заявка↔клиент↔чат.
**Acceptance:** дерево соответствует `visibleNav` для 5 ролей; состояния блоков независимы и сохраняются; активный родитель раскрывается без сброса других состояний; поисковая модалка показывает только доступные узлы; 7 контрольных viewport без horizontal overflow; сценарии S2–S9 сохраняют контекст; табы deep-linkable.
**Тесты:** frontend unit/component, e2e сценариев, role matrix, a11y accordion/search modal, unit URL contract.
**Результат:** целевая навигация и сохранение контекста.

**Предлагаемые подэтапы Phase 2 (отдельные PR):**
1. **2A — Tree & accordion:** Expanded-дерево, независимые состояния, активный родитель, Compact/Flyout, прокрутка.
2. **2B — Search modal:** навигационный поиск по `visibleNav`, keyboard/a11y, граница с будущей palette.
3. **2C — Context Preservation:** URL/history/preferences/drafts, `returnTo`, scroll restoration, Quick Actions.
   **2C.1 реализовано локально:** URL-табы карточек, безопасный `returnTo`, scroll restoration, user-scoped фильтры, очистка при logout. **2C.2 реализовано локально:** Quick Actions (безопасные навигационные команды). **Остаётся:** единый tab component для карточек; Phase 2C в целом не завершена.

### Phase 3 — Command Palette & Recently visited
**Цель:** ускорение опытных пользователей без второго поискового интерфейса.
**Входит:** `Ctrl/Cmd+K`, безопасные навигационные команды, Recently visited (5, TTL 30 дней), entity search с проверкой прав, единый Escape priority и стек модалок.
**Не входит:** мутации данных, вторая иконка поиска, полный глобальный поиск по всем сущностям без метрик.
**Зависимости:** Phase 0–2.
**Риски:** безопасность поиска, hotkey conflicts, дублирование навигационной модалки.
**Acceptance:** поиск respects права; навигационная модалка и palette не конфликтуют; recent скрывает и удаляет недоступное; 2–4 клика сэкономлено на цикле.
**Тесты:** a11y, security unit, e2e palette.
**Результат:** один глобальный вход для безопасных навигационных команд и недавно посещённых разделов. Entity search, история сущностей и Phase 4 остаются отложенными; общий смысл дорожной карты сохранён.

### Phase 4 — Polish & Personalization
**Цель:** визуальная и эргономическая полировка после стабилизации структуры.
**Входит:** анимации и переходы с `prefers-reduced-motion`, пользовательская настройка порядка/состояний, favorites только после метрик, breadcrumbs desktop, контраст dark, density modes.
**Не входит:** workspace switcher, полный redesign карточек и форм, новые бизнес-разделы.
**Зависимости:** Phase 1–3 + телеметрия.
**Acceptance:** метрики подтверждают полезность персонализации; доступность не ухудшилась.
**Результат:** 8.6/10 целевая модель.

**Фактически реализовано в Phase 4 (локально):**
- **Полировка:** компактное меню Rail получило единообразный индикатор группы вместо неоднозначного «···»; убраны лишние анимации/устаревшие комментарии; Command Palette поддерживает стрелки и Enter после перехода фокуса на результат (Tab); сохранены reduced motion, tooltip, flyout, drawer и нижняя навигация.
- **Персонализация:** состояние Expanded и плотность (`compact`/`comfortable`) хранятся per-user в `crm.nav2.prefs.<userId>`, с безопасными значениями по умолчанию и очисткой при logout/смене пользователя. Expanded остаётся доступным только вручную, от 768 px.
- **Глобальная плотность (этап 1):** переключатель записывает `data-density` на `<html>`; в `app.css` определены два набора токенов `--font-*`, `--space-*`, `--control-height`. На токены уже переведены `Button`, `Input` и элементы AppShell. Остальные экраны (>700 жёстких `px`) мигрируются поэтапно — это отдельная будущая работа, не часть текущего этапа.
- **Состояние:** Recently visited повторно проверяется при изменении `visibleNav`/capabilities в открытой сессии; «Очистить недавние» и защита от секретов в URL сохранены.
- **Ограничения:** favorites, breadcrumbs desktop, полный набор density modes и телеметрия не реализованы — favorites требуют метрик, breadcrumbs и расширенная плотность выходят за пределы текущего контракта. Анимации и контраст dark сохранены на уровне существующей дизайн-системы CRM7 без нового redesign.
- **Compact по умолчанию:** каждый блок представлен иконкой первой страницы блока из `visibleNav` (подраздел не подменяет страницу). Настраиваемый набор иконок запланирован отдельной страницей «Настройки меню» в разделе «Настройки системы» и в этом этапе не реализуется.

Каждый phase и подэтап имеет отдельные PR; не объединять Phase 2 и Phase 3 в один релиз.

## 30. Acceptance Criteria

### Navigation
- Для каждой из 5 ролей все доступные пункты видимы в соответствии с `visibleNav`; недоступные скрыты.
- Прямой URL работает; backend security не изменён; недоступные маршруты приводят к существующему `NotFound`/redirect.
- Нет дублирующихся пунктов и двух видимых `nav` с одинаковым `aria-label`.
- Группы открываются/закрываются предсказуемо; `aria-expanded` соответствует фактическому состоянию; конечные пункты ведут по маршруту напрямую.
- Состояния accordion независимы: раскрытие одного блока не закрывает другой; активный родитель раскрывается автоматически без сброса пользовательских состояний.
- Expanded показывает полное дерево с независимой прокруткой; Compact показывает только основные блоки и Flyout по клику.
- Поисковая модалка открывается из Expanded Rail, показывает только доступные `visibleNav` узлы, закрывается по Escape/close/выбору и не дублирует Command Palette.

### Responsive
Проверить 1920 / 1440 / 1280 / 1279 / 1024 / 768 / 767 / 390:
- нет `scrollWidth > innerWidth` на уровне страницы;
- на 1280 и 1024 при Compact Rail нет горизонтального скролла всей страницы; приоритетные колонки таблиц остаются видимыми, остальные данные доступны через адаптивное представление или управляемую прокрутку внутри таблицы;
- rail/bottom/drawer не перекрывают контент;
- 16 px поля на touch-устройствах до 1024 px.

### Accessibility
- Keyboard-only проход всех зон; видимый фокус; tooltip по фокусу; `inert`; Escape priority; screen reader labels; touch ≥44 px; нет keyboard trap.
- Контраст: обычный текст ≥4.5:1, крупный текст ≥3:1, нетекстовые элементы интерфейса ≥3:1 (WCAG 1.4.3 / 1.4.11), включая dark theme.

### Context
- Фильтры, поиск, сортировка, page, табы, thread, `returnTo`, scroll восстанавливаются.
- `returnTo` соответствует контракту §22–23: только `#/…`, ≤128 символов, allowlist, проверка прав, безопасный fallback.
- Deep links и legacy URL продолжают работать без обязательной миграции ссылок либо имеют явно описанный redirect.

### Role matrix
5 ролей × все пункты × desktop/mobile, на контрольных viewport; права не расширяются.

### Regression
Все текущие маршруты: заявки, клиенты, склад/партии, чат, уведомления, корзина, отчёты, настройки, график, профиль, мобильная навигация. Базовый набор URL фиксируется до Phase 1 и используется как контракт совместимости.

### Open questions (требуют прототипа)
1. 64 vs 72 px Compact на 1024–1279 (предварительно: 64 desktop, 72 touch/tablet).
2. Порог Expanded актуализирован: ручной от 768 px, автоматического нет.
3. Хранить состояния accordion в server preferences или localStorage с user-key (предварительно — server preferences вместе с rail state).
4. Хранить recently на сервере или в localStorage с user-key.
5. Длина `returnTo` и формат query для filter set.
6. Нужны ли breadcrumbs на mobile deep pages (предварительно — нет).
7. Нужна ли виртуализация дерева при >50 узлов (предварительно — «Показать ещё» внутри блока).

### Категорически не входит в Navigation 2.0
- Изменение прав, capabilities, backend authorization.
- Изменение API, бизнес-процессов, валидаций.
- Удаление маршрутов и deep links.
- Workspace switcher.
- Именованные сохранённые фильтры (`docs/plan.md` их убрал).
- Полный redesign карточек, форм, таблиц.
- Real-time отправка сообщений; мутации через Command Palette в MVP.
- Favorites без телеметрии.

## 34. Final Decision

**Navigation 2.0 рекомендуется.**
**Окончательная архитектура:** Adaptive Application Rail + Contextual Workspace; серверный Navigation Registry `visibleNav`; Compact с логотипом и Flyout по блоку; Expanded с полным деревом и независимыми accordion; навигационная поисковая модалка; Topbar только со статусными каналами; Contextual Navigation в URL; Entity Navigation внутри карточек; Bottom Navigation на мобильных устройствах из того же реестра.

**Phase 0, Phase 1 и Phase 2 (2A/2B/2C.1/2C.2) реализованы локально.** Phase 3 реализована локально в объёме: единая Command Palette, безопасные Quick Actions и Recently visited по разделам. **Отложено:** поиск по сущностям, Recently visited сущностей, мутирующие команды, Phase 4.

**Отложено:** Command Palette и Recently visited (Phase 3), Favorites, Breadcrumbs на mobile, density polish, персонализация порядка, module-declared contributions.

**Rejected:** Wide Sidebar-first, Workspace switcher, автоматический Expanded, сохранённые именованные фильтры, мутации через palette в MVP, полный redesign карточек, вторая иконка поиска.

**Подтвердить прототипом:** 64 vs 72 px Compact, место хранения accordion-состояний, удобство Flyout на 1024, нужна ли виртуализация дерева.

**Критерии разрешения реализации Phase 2:**
1. Утверждена обновлённая спецификация с моделью ChatGPT-подобного меню.
2. `visibleNav` остаётся единственным источником структуры и видимости.
3. Иерархия «workspace → блоки → подразделы → страницы» не создаёт новых маршрутов и прав.
4. Escape priority и фокус-контракт распространены на accordion, Flyout и поисковую модалку.
5. Существующие URL, сценарии и мобильная навигация покрыты регрессионными тестами.

**В рамках этой задачи код, тесты, конфигурация, стенды и GitHub не изменялись — обновлена только спецификация.**
