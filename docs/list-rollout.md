# Раскатка эталонного списка на другие страницы

Эталон — **CLI-LIST** (`frontend/src/views/Clients.svelte`) и общие компоненты из
`frontend/src/lib/components/{layout,ui}`. Цель раскатки — чтобы любой список в CRM7
имел одинаковую структуру управления и одинаковое поведение, независимо от данных.

**Главное правило:** копировать **контракт**, а не разметку. Разница в функционале и
наборах данных описывается в реестре полей конкретной страницы и в её обработчиках;
общие механизмы (тулбар, модалки, сортировка, пейджер, доступность) берутся из общих
компонентов и **не копируются в страницу**.

---

## 1. Что именно является эталоном

| Область | Эталон | Что переносить |
|---|---|---|
| Шапка | `PageToolbar`, `ToolbarMenu` | Плоская шапка, одно меню «Ещё», порядок действий, чип поиска |
| Поиск | `ToolbarMenu.search` | Модалка с историей/подсказками, «Найти», остановка, очистка, чип |
| Сортировка | `ui/SortDialog.svelte` | Один циклический переключатель на поле, порядок по включению, анонс |
| Модалки | `ui/Modal.svelte`, `ui/FiltersModal.svelte` | Размер `size`, липкий футер, фокус-трап, live-регион внутри диалога |
| Фильтры | раздельные модалки «Вид» и «Фильтры» | Вид — видимость полей, Фильтры — значения; не смешивать |
| Поля | `lib/views/client-fields.ts` | Реестр как единственный источник подписей, типов и брейкпоинтов |
| Список | `Clients.svelte` | Semantic table, мета-строка для скрытых полей, плитки, пустые состояния |
| Пейджер | `ui/Pager.svelte` | Мобильный компактный вид, `per_page=0`, сохранение контекста |
| Токены | `app.css` | `--field-border`, `--focus-soft`, `--control-height-lg`, 24/44 px цели |
| Тесты | `client-fields.test.ts`, `sort-terms.test.ts`, `page-toolbar.test.ts` | Поведенческие тесты правил + строковые guardrail’ы контракта |

## 2. Инвентаризация страницы перед правками

Агент обязан ответить на все вопросы до изменения кода. Ответы фиксируются в задаче/комментарии:

1. **Действия:** какие кнопки/пункты есть сейчас? Что из них дублируется в панели и меню?
2. **Фильтры:** какие фасеты приходят с API? Есть ли зависимости между ними? Какие значения по умолчанию?
3. **Сортировка:** какие поля разрешены сервером (whitelist)? Что такое `defaultValue`? Допустима ли составная сортировка?
4. **Вид:** есть ли таблица/плитки/колонки? Какие поля обязательны? Что показывать на мобильном?
5. **Данные:** как устроены ключи строк, переходы в карточку, возврат `returnTo`, статусы, ожидающие подтверждения?
6. **Права:** кто видит создание/изменение/экспорт? Какие действия скрываются, а не дизейблятся?
7. **Контекст:** какие из `q/page/per_page/filters/view/fields` сохраняются между сессиями? Где — localStorage/серверные `preferences`?
8. **Мобильность:** есть ли специфичные для узкого экрана колонки, чипы, нижняя навигация?
9. **Загрузка:** есть ли гонки запросов, отмена поиска, clamp страницы, fallback при ошибке фасетов?
10. **Отклонения:** что на странице уникально и не укладывается в эталон? Это будет зафиксировано как исключение (см. §8).

## 3. Обязательные правила

### 3.1 Тулбар
- Один `PageToolbar`, плоский, `h1` ровно один.
- Все действия списка — в **одном** `ToolbarMenu`. Порядок пунктов: поиск → сортировка → вид → фильтры → утилиты → CTA.
- Пункты, открывающие диалог, имеют `dialog: true`; переключаемые — `checked` + `role="menuitemcheckbox"`.
- Флаги можно комбинировать: у пункта сортировки есть и `checked`, и `dialog: true`. `ToolbarMenu`
  обязан ставить `aria-haspopup="dialog"` **в обеих ветках** рендера — иначе для
  `menuitemcheckbox` dialog-affordance теряется молча.
- Счётчик активных фильтров — `count`, а не текст в подписи.
- Закрытие по клику вне меню обеспечивается самим `ToolbarMenu`; страница не вешает свой `pointerdown`.

### 3.2 Поиск
- Конфиг `search` в `ToolbarMenu`: `value`, `historyKey`, `title`, `placeholder`, `suggestions`, `onsearch`, `onclear`, `onstop`.
- `onsearch` — `async` и **дожидается реальной загрузки**, иначе кнопка «Остановить» не появится.
- `onstop` отменяет запрос через `AbortController` → `signal` в API-клиенте. `AbortError` гасится в странице, но не превращается в сетевую ошибку.
- Активный поиск показывает чип с кнопкой очистки. Очистка сбрасывает `q` и `page=1`.
- Сохранение контекста: `saveClientFilters()`-аналог вызывается **после** сброса `page = 1`, до/при загрузке; `q`, `page`, `per_page` обязательны.

### 3.3 Сортировка
- Только общий `SortDialog`. Локальные модалки сортировки, drag-ручки, две стрелки на поле и кнопки приоритета — **запрещены**.
- На поле — один циклический переключатель `выкл → ↑ → ↓ → выкл`; приоритет = порядок включения.
- `fields` — whitelist, совпадающий с серверным. Для составных имён полей разбор термина — через `lastIndexOf('_')` (`lib/views/sort-terms.ts`).
- `onapply` обязательно закрывает диалог. `defaultValue` — сортировка по умолчанию страницы/вкладки.
- Анонс полного порядка и позиции условия — внутри `Modal` (`announcement`).

### 3.4 Вид и фильтры
- Две разные модалки. «Вид» отвечает за видимость полей и способ отображения, «Фильтры» — за значения.
- «Сбросить» в «Виде» возвращает дефолт текущего брейкпоинта и сбрасывает `viewExplicit`.
- У чекбоксов «Вида» обязательные поля отмечены и недоступны для снятия.
- Мобильный список показывает **ровно** выбранные поля; скрытые колонки уходят в мета-строку с `aria-describedby`.
- Модалка «Вид» применяет изменения сразу и имеет одну кнопку `Готово` (или «Применить»),
  **без** «Отмена»: откатывать уже сохранённое состояние бессмысленно.
- Футер **фильтровых** модалок (фильтры, сортировка): `Сбросить` (`text`, lg) у левого края;
  `Отмена` (ghost) → `Применить` (primary) в правой группе `.modal-buttons`. На ≤720 px кнопки
  идут одним рядом равной ширины, на ≤480 px последняя переносится на всю ширину — оба правила
  живут в `app.css`, локальные `flex-wrap` их не перебивают.

### 3.5 Реестр полей
- На каждом списке — свой реестр по образцу `lib/views/client-fields.ts`. Одна запись описывает:
  `key`, `label`, `headLabel`, `required`, `minWidth`, `width`, `headClass`, `cellClass`, `value`,
  `title`, `kind`, `muted`, `ellipsis`, `tileRegion`, `tileClass`, `primary`, `empty`.
  От `muted`/`ellipsis`/`primary` зависят усечение и акцент в плитках — терять их нельзя.
- Шапка, ячейки, плитки и мета-строка рендерятся `{#each}` по дескрипторам. Отдельная карта ширин в странице **запрещена** — `width` лежит в реестре.
- Обязательные поля с нестандартной разметкой (ссылка, счётчик, чипы) остаются в странице, но их подписи и порядок тоже берутся из реестра.
- Legacy-значения (например, `contacts`) нормализуются в реестре, а не в разметке.

### 3.6 Таблица и список
- `role="table"` / `row` / `columnheader` / `cell`; число заголовков == числу ячеек == числу треков сетки на всех брейкпоинтах.
- Один tab stop на строку, ссылка с `aria-describedby` на мета-строку.
- Загрузка guarding: `loadSeq` или `AbortSignal`; устаревший ответ не применяется; `error` не читается как результат конкретной гонки — `load()` возвращает `{ok, total}`.
- `page > maxPage` → clamp с повторной загрузкой и сохранением контекста.
- Пустые состояния различают «нет данных» и «ничего не найдено», с разными действиями.
- Ожидающие подтверждения свёрнуты до трёх с кнопкой «Показать все».

### 3.7 Пейджер и возврат
- Общий `Pager`, `per_page=0` («Все») поддерживается и сохраняется.
- Переходы в карточку — через `withReturnTo`; возврат из карточки — через `normalizeReturnTo`.
- Кнопки и `select` визуально компактны на мобильном, но сохраняют 44 px зону через псевдоэлементы.

### 3.8 Доступность
- `role="dialog"` + `aria-modal`, фокус-трап, возврат фокуса, изоляция вложенных диалогов.
- Live-регион анонсов — внутри диалога; дублирующийся видимый текст — под `aria-hidden`.
- Видимый текст кнопки/подписи входит в `aria-label` (2.5.3).
- Контраст: `--primary-hover` ≥4.5:1 к `--on-primary`, `--field-border` ≥3:1 к `--surface`.
- `:focus-visible` не перебивается локальным `:focus { outline: none }`.
- Цели ≥24 px, на `pointer: coarse` — 44 px; gap между целями ≥ расширения псевдоэлемента.
- Фокус — внутренний акцент `var(--focus-soft)` через `box-shadow: inset`, не внешний
  `outline` с положительным offset (тот обрезается краями контрола).

### 3.9 Стили
- Локальные `:global()`-переопределения на страницах **запрещены**: значения живут в общих
  компонентах и токенах `app.css`.
- Жёсткие `font-size`, `padding`, `border-radius`, `transition` заменяются токенами.
- Мобильное переопределение обязано повторять селектор базового правила и лежать в конце
  `<style>`: если базовый селектор `.it-row.prices`, в медиазапросе пишем
  `.it-row, .it-row.prices { … }`, иначе специфичность ниже и правило не сработает.
- Кнопки футера на ≤720 px — один ряд равной ширины (общее правило `app.css`).

## 4. Что менять нельзя

| Нельзя | Почему |
|---|---|
| API-контракты, whitelists сортировки, статусы, роли | Это данные и права, а не UI |
| Маршруты и параметры URL | Нарушает returnTo и закладки |
| Пользовательские настройки других страниц | Переносим только свою страницу |
| Подписи/тексты в эмоциональном стиле | Сохранять терминологию продукта |
| Коммитить, пушить, мержить, деплоить | Изменения остаются незакоммиченными до ревью |
| Копировать старые паттерны из соседних страниц | См. §7 |

## 5. Порядок работы агента

1. Прочитать `AGENTS.md`, `docs/ui.md`, этот документ и эталонный `Clients.svelte`.
2. Провести инвентаризацию (§2) и зафиксировать ответы.
3. Сверить текущее состояние: `git status -sb`, `git log --oneline -5`. Чужие правки не откатывать.
4. Вынести реестр полей страницы; убрать локальные карты ширин и `{#if}`-гейты из разметки.
5. Перевести тулбар на `PageToolbar` + один `ToolbarMenu`; подключить `onstop`, `dialog: true`, `count`.
6. Перевести сортировку на общий `SortDialog`; проверить whitelist и `onapply` (закрытие).
7. Разделить «Вид» и «Фильтры», привести футер к эталону.
8. Привести таблицу/плитки к семантике и мета-строке; добавить load guards и clamp.
9. Проверить мобильный режим, тёмную тему, compact и 44 px цели.
10. Добавить поведенческие тесты для чистых правил и smoke-сценарий e2e для ключевого действия;
    обновить явные списки страниц в `page-toolbar.test.ts` и `modal-offset.test.ts`, иначе
    раскатанная страница не попадёт под контрактную регрессию.
11. Прогнать проверки (§6), переснять скриншоты и приложить их к задаче.
12. Отдать на независимый аудит (функциональность + a11y + контракт). Только после зелёных вердиктов считать страницу раскатанной.

## 6. Обязательные проверки

```bash
cd frontend
npm run check
npm test
npm run build
git diff --check
```

Smoke e2e (поднять локальный стенд, см. `AGENTS.md`). `run-dev.cmd` подбирает свободные
порты (часто API `:8090`, фронт `:5180`), поэтому адреса задаются через env, а не захардкоживаются:

```powershell
$env:CRM_BASE_URL='http://localhost:<порт Vite>'
$env:CRM_API_URL='http://127.0.0.1:<порт API>/api/v2'
$env:CRM_PASSWORD='Secret123'
$env:CRM_BROWSER_CHANNEL='chrome'
$env:CRM_E2E_SMOKE='1'
npm run e2e
```

Обязательные CI-гейты из `docs/testing.md` — **не подменять ручным просмотром**:

- Lighthouse Fast 3G: performance ≥80, LCP ≤2.5 с, CLS ≤0.1, TBT ≤300 мс (`npm run lighthouse`).
- Мобильный e2e: `CRM_E2E_MOBILE=1 npm run e2e` (viewport 390×844, touch, плитки и мета-строки).

Дополнительно вручную: 360 / 720 / 721 / 900 / 1024 / 1200 px, тёмная тема, compact,
клавиатурная навигация по меню и диалогам, «Остановить» поиск на медленном ответе,
возврат из карточки после поиска и перелистывания.

## 7. Типичные ошибки (устаревшие паттерны)

- Локальная модалка сортировки с `sort-drag`, `ondrop`, парой `dir-btn`.
- Кнопки «Фильтры»/«Вид» прямо на странице вместо пунктов `ToolbarMenu`.
- Два модалых заголовка «Вид» или подсказка, дублирующая подпись поля.
- `aria-haspopup="true"` + `role="group"`; `aria-label`, перебивающий видимую подпись.
- Жёстко заданные `font-size`, `padding`, `border-radius` вместо токенов.
- `saveClientFilters()` до сброса `page = 1`; не сохраняется `q` при перелистывании.
- `per_page=0` не разрешён в whitelist сохранения.
- `load()` без guard’а: старый ответ перезаписывает новый.
- E2E-ожидания старого DOM. Актуальные варианты: навигация через `.rail-nav` / `nav.tree`,
  «Журнал аудита» — ссылка в flyout группы «Система» (обычная проверка — негативная:
  у менеджера ссылки нет), «Вид и фильтры» — актуально для `Staff`, но не для `Substitutions`.

## 8. Исключения

Если страница не укладывается в эталон, исключение **обязательно** фиксируется в
`docs/ui.md` рядом с описанием эталона: что именно отличается, почему и какой компонент
за это отвечает. Нельзя «просто не делать» — следующая страница скопирует молчаливое
отклонение как правило.

Пример корректного исключения: брейкпоинты 1200/1024/900/720 для таблицы клиентов —
локальное отличие от общего канона 1024/1600.
